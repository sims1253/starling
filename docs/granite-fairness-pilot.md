# Granite chunk fairness CPU pilot (#178)

This report evaluates the opt-in `--granite-chunk-fairness` scheduler in [#178](https://github.com/sims1253/starling/issues/178). The prerequisite is a real-model mixed-request delay on the current serial server. The earlier [#174 pilot](serving-contention-pilot.md) found one, but its scored WebSocket sessions had completed only the transport handshake. The corrected runs here require an application `ping`/`pong` before each long upload, so the measured short-request delay begins with a ready session. The final reviewed binary passed the preregistered three-pair CPU comparison and a distinct-audio A/B/A output-isolation check. This is not a p95/p99 estimate or a recommendation to change the default.

## Method and decision rule

The baseline and candidate used the same Granite Speech 4.1 2B BF16-exact GGUF (SHA-256 `b72a01687daa1825894bd5ea3e4c53f6be657a9ba31c5cd65c5114c5b6b961e2`) and the public `tests/fixtures/short.wav` (7.435 s, SHA-256 `5fceacff0315d49cb59fcc505bcecf1ed5f2f35c2897b1e65a59f30e5d922150`) and `tests/fixtures/long.wav` (74.35 s, SHA-256 `4f97080176d3623eebc9663af07dd258894ed31f74d5d229d39e77c5ab5b0925`). The long input repeats the short source ten times and ends with a partial Granite chunk. Each server process warmed on the short WAV. Six trials per arm alternated idle short WebSocket dictation and a mixed trial that started the long HTTP upload before sending the short WebSocket audio. The stop-to-final clock starts after sending the short frame. The client retries a `server busy` commit once per second in the serial arm. The harness records trace, HTTP status and final-text hashes; it does not store transcripts.

The host was an AMD Ryzen 9 5900X under Linux 6.18.33.2 WSL2. Each native CPU server was pinned to logical CPUs 16–23 with `OMP_NUM_THREADS=8` and `STARLING_TRACE=1`; unrelated CPU work was assigned outside those cores. Affinity does not remove shared-cache or host-load effects. The serial binary SHA-256 was `a91847c520596042e798e5acd17e14c3ada78a7b3699f317b4402d5459cf6d49`, built from `master@6b95f3477f04aef2d0ee99a95132f311fb45de61` with this repo's pinned ggml and patches. The initial candidate binary SHA-256 was `42e90a5b75c69662542b1d7518791782cc29e7ec460a1000ace3d38e8c81b0dc`, built from the fair-scheduler source at `4121728`. The current final-binary replication is pinned to `57c54ab3638211b36720a97615af175e950bce6d7e5f5a59a98364d16435f713`, built from `a3fd822`.

The corrected baseline was specified in `benchmarks/contention/serial_ready_spec.json` (SHA-256 `49c5d28c52aeb448234fb427b537b19ddf89d4fdac5aa781d426c1eb69a3c3b0`). The matched comparison rule was committed in `benchmarks/contention/fairness_comparison_spec.json` at `56a59b0` before candidate timing. After the baseline and before the first candidate timing, the candidate was rebuilt with the final reservation and lock-free job-creation fixes; commit `aba1e56` re-pinned only its binary hash in [`benchmarks/contention/fair_ready_spec_initial.json`](../benchmarks/contention/fair_ready_spec_initial.json) (SHA-256 `974f97d79fc1f050b808a86dbce61f1caf4c5a526a17c8d1baad323a45ef2bcd`). The thresholds were unchanged. Each pair had to re-establish serial material contention; the candidate then needed a successful final at least 20 s and 25% sooner than serial mixed, zero busy replies, the exact same short and long text hashes, successful three-chunk HTTP long upload, and long wall time at most 1.35 times its serial pair. Missing or failed attempts were not excluded. The same rule will evaluate the post-review binary against the saved serial baseline.

Run `benchmarks/contention/run_pilot.py` with `--spec benchmarks/contention/serial_ready_spec.json` for the serial binary and `--spec benchmarks/contention/fair_ready_spec.json --server-arg=--granite-chunk-fairness` for the candidate, passing the pinned binary, GGUF and WAV paths. `benchmarks/contention/evaluate_fairness.py --serial SERIAL/result.json --fair FAIR/result.json` applies the current final-binary gate. Pass `--candidate-spec benchmarks/contention/fair_ready_spec_initial.json` when checking the saved initial candidate; the default deliberately rejects that historical result because its binary spec differs. The scripts verify binary and input hashes before timing. The unmodified result summaries are committed at [`benchmarks/contention/results/serial-app-ready-cpu-2026-09-27.json`](../benchmarks/contention/results/serial-app-ready-cpu-2026-09-27.json) and [`benchmarks/contention/results/fair-app-ready-cpu-2026-09-28.json`](../benchmarks/contention/results/fair-app-ready-cpu-2026-09-28.json); raw trace logs remain in the local run directories.

Its [partial result](../benchmarks/contention/results/interrupted-fair-partial-2026-09-28.json) and [interruption record](../benchmarks/contention/results/interrupted-final-attempt-2026-09-28.json) are preserved. ## Final-binary replication (2026-09-28 UTC)

The final candidate binary (`57c54ab3638211b36720a97615af175e950bce6d7e5f5a59a98364d16435f713`) ran six fresh app-ready trials against the saved serial baseline. The candidate's own `run_pilot.py` verdict is `inconclusive` because that baseline-only verdict requires busy retries and a single long service record, which the fair scheduler intentionally removes. The predeclared paired decision is instead `evaluate_fairness.py`; it returned `pilot_pass` with no failed rule using the current pinned candidate spec. Every trial returned the same short final hash and each mixed long request returned HTTP 200, the same long final hash, and three traced chunks.

## Initial distinct-audio state-isolation check

The separate A/B/A rule was pinned in [`benchmarks/contention/real_ab_a_spec_initial.json`](../benchmarks/contention/real_ab_a_spec_initial.json) (SHA-256 `71f5a8eaff15c37d4d3980ca90eb92babb3585bfc35703f834cba015f578789e`) before its first run. Input A was the same 74.35 s public repeated LibriSpeech fixture used above. Input B came from a [different public LibriSpeech clip](https://huggingface.co/datasets/argmaxinc/librispeech/resolve/main/1089-134686-0000.flac) (FLAC SHA-256 `30885601173f96b0d8ddd020dc959b055c6c1582b85a33e3fcab8c4b08ed94c2`), decoded to mono 16 kHz PCM16 WAV with FFmpeg 4.4.2 and repeated seven times at the PCM-frame level. The resulting 73.045 s B WAV (SHA-256 `16503e95c0a78cc4fbd2db3789d385297bc31ad52e63ef79e8bbe5040fb01be4`) also ends with a partial third chunk. These inputs differ in source speech and in final-text hash; neither contains personal audio.

With the same model and reserved CPU cores, the serial binary transcribed A then B as independent controls. The fair binary started A1, then queued B and A2 during A1's first active chunk. The preregistered pass required HTTP 200 and chunks `[1,2,3]` for all five requests; serial A's final hash had to equal fair A1 and A2, serial B's had to equal fair B, and A and B had to differ. B and A2 first chunks had to execute between A1 chunks 1 and 2. A fresh WebSocket session opened during A1's first chunk also had to answer an application ping in under 2 s. The runner saves hashes and trace order, not transcripts.

| Input | Serial final SHA-256 | Fair final SHA-256 | Serial / fair HTTP wall |
| --- | --- | --- | ---: |
| A → A1 | `8bd0f0a220db9523f2cdf545de2281e9c4e1ec6bddebe6f8ad4bb133d54745dd` | same | 86.83 / 234.31 s |
| B | `693595171fcf8fa1dc621ddeec55db226e46f62318ca66224660083dfb191dc4` | same | 114.62 / 258.57 s |
| A2 | same A reference | same A reference | — / 287.56 s |

All five requests returned HTTP 200 and traced exactly three chunks. The fair chunk order was `A1, B, A2` in each of rounds 1, 2 and 3, with one active chunk at a time. The fresh WS handshake took 1.73 ms and its application ping/pong took 41.06 ms during A1's first chunk. `real_ab_a.py` returned `pass` for output hashes, chunk counts, interleaving and admission. The unmodified summary, including the complete chunk order, is [`benchmarks/contention/results/real-aba-cpu-2026-09-28.json`](../benchmarks/contention/results/real-aba-cpu-2026-09-28.json); local trace logs were saved beside it during measurement. The three fair uploads shared one engine, so their individual HTTP wall times include waiting behind other jobs and should not be compared with the two sequential serial controls as a like-for-like throughput estimate.

## Scope and limits

The flag remains opt-in and the engine still executes at most one chunk at a time under the C API runtime lock. Cancellation and timeout discard partial transcripts. No user audio or personal data was used. Three matched CPU pairs cannot establish a latency distribution, GPU behavior, multi-session overload fairness, or correctness across every audio/model combination. The broader workload matrix remains in [#174](https://github.com/sims1253/starling/issues/174).

This pilot uses FIFO turns; it does not implement #178's interactive priority with aging or weighted fairness. The measurements also do not bound starvation under sustained arrivals. Those scheduler and workload requirements remain follow-up gates before #178 can be considered complete or the flag can become a default. `pilot_pass` applies only to the paired CPU rule above.
