# Kernel verification: measured CUDA boundary tier and next proof boundary

Issue [#32](https://github.com/sims1253/starling/issues/32) proposed three independently mergeable tiers. This note records what the first tier actually checks and where the later proof proposals need a tighter specification. The Python project describes itself as a deprecated research backend in `pyproject.toml`; the native serving engine is separate.

## CUDA boundary tier

`tests/test_cuda_kernel_boundaries.py` executes all eight kernels in `src/starling/_kernels/cuda/backend.cu`: RMSNorm, SiLU-multiply, residual-add, RoPE, rstd, FP8 GEMV, normscale GEMV and FP4 GEMV. It covers positive widths around 32/128/256/1024 thread or data boundaries, odd tails, one-element inputs, multiple rows or heads, a two-batch RoPE case and supported strided activation views. The independent PyTorch backend supplies numerical reference outputs. Numerical tolerances for reductions and quantized GEMV follow the existing kernel contract; these comparisons do not assert byte equality where the reduction order differs.

Zero-length inputs are rejected before the CUDA extension is called. They do **not** enter the sanitizer corpus as N=0 launches. RoPE rejects head dimensions other than 128 because the compiled launcher uses `rope_kernel<128>` and 128 threads unconditionally. The wrappers also reject short GEMV activation buffers and incompatible shapes or packed scales before those buffers reach a kernel. Direct calls to the private PyTorch extension are outside these wrapper checks.

Run `uv run python scripts/sanitizer_gate.py` on a CUDA host. It launches each NVIDIA Compute Sanitizer tool in a fresh process, fails on missing hardware/tool, test failures, sanitizer errors or timeouts, and writes separate logs plus a JSON summary under `outputs/sanitizer/`. [NVIDIA's Compute Sanitizer manual](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html) defines memcheck as memory-access checking, initcheck as uninitialized global-memory checking, racecheck as shared-memory hazard checking and synccheck as synchronization-primitive checking. Racecheck does not certify all global-memory races; no finite input corpus proves all shapes.

On 2026-09-27 UTC, the boundary corpus passed all four tools on an RTX 5090 with CUDA 13.0 and PyTorch 2.13.0+cu130. Each tool reported zero errors; racecheck reported zero hazards. The corpus is an executable local gate. This repository had zero configured GitHub self-hosted runners at the time of the run, so there is no claim that a GPU CI job passed. The native ggml engine replays in #32 and native replay-boundary work in [#172](https://github.com/sims1253/starling/issues/172) are outside this Python CUDA corpus.

## Equivalence tier assessment

The six proposed elementwise or reduction operators are useful candidates for proof experiments, but “same real-arithmetic skeleton and same truncation points” does not imply byte equality for compiled floating-point kernels. Accumulation order, fused multiply-add, NaNs, infinities, signed zero and compiler transformations must be part of the accepted semantics. A handwritten Z3 formula can prove its own encoding without establishing that the compiled PTX implements that encoding. [VOLTA's paper](https://arxiv.org/abs/2511.12638) addresses equivalence at PTX level for a defined structured-kernel class; that is a relevant prior, not a proof of Starling's kernels. The first credible follow-up is one narrowly scoped operator with a source/compiled-kernel connection, a stated IEEE or deliberately restricted input contract, mutant counterexamples and explicit `unknown` on unsupported cases.

The issue's proposed `bench_autotune.py` integration point has also changed: `benchmarks/parakeet/bench_autotune.py` currently sweeps decoder replay length K, not candidate CUDA kernel arithmetic or launch configurations. A proof gate for structural CUDA rewrites needs an actual kernel-candidate acceptance path. No such production gate is added here.

## ggml graph tier assessment

Graph translation validation has a different trust boundary: exporting a ggml DAG is only a topology check until each op's shape, stride, dtype, rounding, aliasing and weight semantics are modeled. Comparing an exported graph to itself is a smoke test, not independent validation. A bounded solver check must report `unknown` outside its bound. [VOLTA](https://arxiv.org/abs/2511.12638) is PTX scoped, and [ProofWright](https://arxiv.org/abs/2511.12294) studies CUDA kernels; neither establishes equivalence for Starling's ggml graphs. Start with a small decoder-step subgraph and a known wrong-index mutant before claiming an optimization gate. This research remains open; it should be prioritized against the native engine's current optimization needs.
