# Plan: Cross-platform Starling (Linux + Windows, all 10 models)

## The core problem, precisely

The **only** thing blocking Windows is **Triton** (no official Windows wheels for the resolved version; experimental at best). Per the audit:

- **Parakeet (both), Cohere** — use **zero** Triton. Blocked *only* by `triton>=3.6` being a hard dep so the install fails.
- **Moss, Granite, Qwen3, ARK, Audex, Nar, Higgs** — use hand-written Triton kernels for a handful of small elementwise ops (`rmsnorm`, `silu_mul`, `residual`, `rope`) + the opt-in `fp8_gemv`. These are imported at module top-level, so import fails without Triton.

Everything else (CUDA graphs, the server, model pipelines, cuBLAS GEMMs) is already portable. There is **no NeMo, no flash-attn, no Linux-only syscall in the core**. The recent `perf(moss)` commit already *removed* the worse Windows blocker (`torch._scaled_mm`).

The kernels are consumed through **narrow, uniform interfaces** (`_k.fused_rmsnorm(...)`, `_k.fused_silu_mul(...)`, `fp8_linear(...)`) and the project already has the `OptFlags` switchboard pattern. That's the seam for a backend abstraction.

**Key insight that makes this tractable:** the 3 Moss elementwise kernels operate on 4 KB tensors (hidden=2048) and run **inside a CUDA-graph capture**, so Triton's launch-overhead win is *already* eliminated by graph replay — the only residual benefit is fewer memory passes over L2-resident data, which may be negligible. The fp8 GEMV is the one place where performance genuinely matters, but it's **opt-in** (`fp8_weights=False` by default; only `--profile batch`). The user's primary dictation use case (`--profile realtime`) **never touches fp8**.

**Byte-exactness:** goldens are captured from the eager PyTorch reference (`reference.py`), not from Triton. A stock-PyTorch fallback replicates the reference's op semantics, so it is likely *more* byte-exact with golden than Triton is. The harness confirms this.

**Mac (Apple Silicon) is explicitly out of scope.** The architecture is built on `torch.cuda.CUDAGraph`, which is NVIDIA-only; MPS doesn't support graph capture. Mac would need a separate non-graph codepath — a much larger project. This plan delivers the user's hard requirement: **native Linux + Windows**.

## Architecture

A new `src/starling/_kernels/` package provides a uniform kernel interface with pluggable backends. Per-model `llm_kernels.py` and `fp8*.py` files become **2-line re-export shims** so **zero consumer code changes** (`from . import llm_kernels as _k` keeps working).

```
src/starling/_kernels/
  __init__.py          # public API + get_backend() auto-selection
  base.py              # KernelBackend protocol (signatures + docstrings)
  triton_backend.py    # ALL triton kernels unified (granite+moss+higgs+fp8+fp4)
  torch_backend.py     # PyTorch-native fused ops (Windows default)
  cuda_backend.py      # (iteration 4) load_inline CUDA C++ — only if bench says so
  _compile.py          # torch_compile() helper: no-ops when triton absent
```

Backend selection: `OptFlags.kernel_backend: str = "auto"` (`auto|triton|torch|cuda`); `auto` = triton if importable else torch. Server CLI `--kernel-backend`. Benchmarks import backends directly to A/B.

Unified interface (union of all kernels; moss's plain-add residual = `residual_add(x,y,alpha=1.0)`):
- `fused_rmsnorm(x, weight, eps)`, `fused_silu_mul(gate, up)`, `residual_add(x, y, alpha=1.0)`
- `fused_rope(q, k, cos, sin)` (provided everywhere; moss already doesn't use it by default)
- `fp8_linear(x, w_fp8, scale)`, `quantize_weight_e4m3(weight)`
- `fp4_linear(...)`, `quantize_fp4(...)` (granite; experimental, off by default)
- `compute_rstd`, `gemv_normscale` (granite CODA; experimental, off by default → simple-but-correct torch fallback, no perf claim)

## Dependency change (one line)

`pyproject.toml:9`:
```toml
"triton>=3.6 ; sys_platform == 'linux'"   # was: "triton>=3.6"
```
On Windows, triton simply isn't installed; `get_backend()` detects its absence and uses the torch backend. If someone manually installs `triton-windows` fork, auto-detection picks it up. cu130 torch wheels already exist for `win_amd64`, so the Blackwell pin works on Windows too.

## Iterations (each is independently shippable; benchmark-driven)

### Iteration 0 — Scaffold & make Triton optional
**Files:** new `src/starling/_kernels/{__init__,base,_compile}.py`; edit `pyproject.toml:9`.
- `base.py`: `KernelBackend` Protocol with the unified signatures above.
- `__init__.py`: `have_triton()` (guarded import), `get_backend()` → returns the right module, re-exports the public functions for shims.
- `_compile.py`: `torch_compile(fn, mode, **kw)` returns `fn` unchanged when `have_triton()` is False; else `torch.compile(...)`.
- `pyproject.toml`: add the `; sys_platform == 'linux'` marker.
- Add `kernel_backend` field to `OptFlags` (`flags.py`) + the `flags()` context-manager field list (line ~265).
**Verify:** `pip install` succeeds on a no-triton env; `import starling` doesn't import triton at module load.

### Iteration 1 — Triton backend (move & unify)
**Files:** `src/starling/_kernels/triton_backend.py`; rewrite the 3 per-model `llm_kernels.py` + 2 `fp8*.py` + `fp8_gemv.py` as shims.
- Move all kernels into `triton_backend.py`, unifying: moss's `fused_residual` → `residual_add(x,y,alpha=1.0)`; higgs copy deduped into the granite set. Consolidates **3 copies → 1** (reduces divergence risk flagged in audit).
- Each `llm_kernels.py` becomes: `from .._kernels import fused_rmsnorm, fused_silu_mul, residual_add as fused_residual, fused_rope`.
- `fp8.py` / `fp8_gemv.py`: repoint to `_kernels`. (Benchmarks importing `fp8_gemv` keep working via re-export.)
- **Zero changes to consumer files** (`llm_mega.py`, `fused_decode.py`, etc.) — they still do `from . import llm_kernels as _k`.
**Verify:** full existing test suite passes unchanged on Linux (byte-exactness vs golden unchanged — same kernels, just relocated).

### Iteration 2 — PyTorch fallback backend (Windows works)
**Files:** `src/starling/_kernels/torch_backend.py`.
- Implement each fused op with stock PyTorch matching the reference's fp32 semantics:
  - `fused_rmsnorm`: `x.float(); var=x.pow(2).mean(-1,keepdim=True); (x*rsqrt(var+eps)).to(x.dtype)*weight`
  - `fused_silu_mul`: `F.silu(gate.float()).to(gate.dtype)*up`
  - `residual_add`: `x + alpha*y`
  - `fp8_linear`: dequant-then-`F.linear` (correct, not fast — materializes bf16 weight)
- Make `torch.compile` call sites safe: replace `torch.compile(...)` → `torch_compile(...)` at the ~7 sites (parakeet `encoder_graph.py:380`, moss `llm_mega.py:132`, qwen3/audex/higgs/nar multistep/decode). All are opt-in; now gracefully no-op without triton.
- `get_backend()` returns `torch_backend` when triton absent.
**Verify:** `import starling.moss`, `import starling.granite` succeed in a no-triton env; existing byte-exactness tests run against the torch backend (expect byte-exact or within 1 ULP).

### Iteration 3 — Correctness + benchmark harness (decision gate)
**Files:** `tests/test_kernel_backends.py`; `benchmarks/bench_kernels.py`.
- `test_kernel_backends.py` (parametrized, CUDA, skip if no triton): for each kernel at real decode shapes (M=1, N=2048/4096), assert `torch_backend` output matches `triton_backend` within tolerance (max-abs diff); also assert each matches the reference op. This is the correctness gate for the Windows fallback.
- `bench_kernels.py` (matches existing `bench_leaderboard.py` tabulated style):
  - Per-kernel A/B (triton vs torch) latency + max-abs-diff at decode shapes.
  - End-to-end: Moss + Granite decode latency, triton vs torch backend, on the same audio.
- **Decision output:** a table showing the "Windows tax" per kernel. This tells us *exactly* where (if anywhere) a CUDA kernel is worth writing.
**Verify:** harness runs on the Linux/RTX-5090 box (both backends available); produces the cost table.

### Iteration 4 — (Conditional) CUDA C++ kernels for hotspots
**Only if Iteration 3's table shows a real loss on Windows** (likely candidate: `fp8_gemv` in batch profile; the 3 elementwise kernels likely show negligible difference inside graph replay).
**Files:** `src/starling/_kernels/cuda_backend.py` + `cuda/kernels.cu`.
- `torch.utils.cpp_extension.load_inline` for the hotspots. CUDA C++ compiles cross-platform (MSVC on Windows, gcc on Linux). First-run JIT compile (cached).
- Wire into `get_backend()` when `kernel_backend="cuda"` (and as `auto`'s fp8 choice on Windows if it beats the torch dequant fallback).
**Verify:** `test_kernel_backends.py` extended to cover cuda backend; bench shows parity with triton.

### Iteration 5 — Windows packaging, setup & CI
**Files:** `scripts/setup_env.py` (cross-platform replacement for `setup_env.sh`); guard `scripts/bench_memory.py:23` (`import resource`); new `.github/workflows/test.yml` matrix `{ubuntu-latest, windows-latest}` running `test_server_routing.py` + import-correctness on both OSes (heavy GPU tests stay manual).
- `setup_env.py`: uses `.venv/Scripts/python.exe` vs `.venv/bin/python` per platform; skips triton import check on Windows.
- `bench_memory.py`: guard `import resource` behind `os.name == 'posix'` (use `psutil` or `0.0` fallback on Windows).
- README: add a "Windows" install/run section.
**Verify:** `python -m starling.server --model moss` starts on native Windows (no WSL2); the freestyle app connects to `localhost`.

## Success criteria (completion audit)

1. `pip install` of starling succeeds on Windows (no triton). → check `pyproject.toml` marker + a no-triton install.
2. `import starling.moss` / `.granite` / `.parakeet` succeed without triton. → runtime check.
3. All existing byte-exactness tests pass unchanged on Linux with the triton backend (Iteration 1 regression check).
4. `test_kernel_backends.py`: torch backend matches triton within tolerance per kernel (Windows correctness).
5. `bench_kernels.py` produces the triton-vs-torch cost table (decision gate for Iteration 4).
6. `python -m starling.server --model moss` runs natively on Windows; `--model parakeet-tdt-0.6b-v3` runs natively on Windows.
7. Existing Linux performance is preserved (no regression from the refactor — verified by the bench harness comparing pre/post on Linux).
